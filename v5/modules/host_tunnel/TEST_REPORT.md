# Проверки туннелей хоста

Стенд: отдельные Debian 12/13 внутри QEMU/WSL, без подключения к рабочим
серверам. Архивы модулей подписаны отдельным учебным ключом. В образе
ядра есть код адаптеров и неактивные unit-файлы, но нет конфигурации,
закрытых ключей или бинарников туннелей.

| Debian / ядро | Инструменты | Подтверждено до reboot |
| --- | --- | --- |
| 12 / `6.1.0-54-cloud-amd64` | WG `v1.0.20210914`, AWG `v3.1.20260812`, kernel AWG `1.0.0` из закреплённого тега `v3.1.20260906` | Подписанная установка без запуска; причина при скрытых модуле/заголовках; настоящий WG, AWG legacy и AWG 3.1; peer-only `syncconf` сохраняет ifindex; проверка параметров 3.1 через `setconf` и `showconf`; закрытие портов и IPv4 NAT обоих модулей. |
| 13 / `6.12.115+deb13.1-cloud-amd64` | Та же связка; модуль собран для другого текущего ядра | WG/AWG legacy/AWG 3.1 handshake и UDP; peer-only `syncconf`; отсутствие зависимостей не нарушает доступ к порталу; закрытие своего UDP-порта и сохранение второго туннеля; IPv4 NAT обоих модулей и защита чужого интерфейса. |

Обе VM перезагружены, проверен новый boot ID. Портал доступен, его учётная
запись и TLS-ключ сохранены. Выключенные туннели не открыли UDP-порты после
загрузки. После повторного включения оба реальных клиента подключились с
прежними ключами и адресами. E2E и дополнительная проверка readback AWG 3.1
в ограниченном systemd Debian 13 завершились с exit=0.

## Что выявил стенд

- `ip link add ... alias ...` не гарантирует метку у нового устройства.
  Адаптер создаёт временное выключенное устройство, присваивает метку
  и только после этого назначает рабочее имя `wg0` или `awg0`.
- nftables 1.0.6 сохраняет комментарий владельца, но не выводит его в
  JSON. Адаптер сверяет семейство, имя и handle таблицы в JSON и принимает
  только её собственный верхнеуровневый комментарий в текстовом выводе.
- `modinfo` у upstream-сборки может сообщать `1.0.0` независимо от тега.
  Для 3.1 проверяются опции tools и фактические применённые настройки
  временного выключенного интерфейса без адреса и порта.

## Воспроизведение

`tests/v5/prepare_tunnel_lab.py` устанавливает зависимости только на
проверенной учебной VM и собирает исходники закреплённых upstream-коммитов.
`tests/v5/tunnel_lab_e2e.py` переносит проверенный архив ядра, подписывает
пакеты, запускает `check_tunnel_vm.py`, отдельный NAT-сценарий и при
`--reboot` проверяет восстановление с исходными ключами. Не запускайте
эти fixtures на рабочих серверах.

В WSL `tunnel_egress_e2e.py wireguard` проходит в отдельных mount и
network namespaces: `PYTHONPATH=. unshare --mount --net --propagation private
python3 -m tests.v5.tunnel_egress_e2e wireguard` (одной строкой). Это
дополнительная проверка WireGuard, а не доказательство AWG.

Инженерные проверки WSL: architecture/compileall и scoped diff — exit=0;
106 тестов v5 — exit=0; 39 legacy-тестов — exit=0, 1 явный skip старого
Docker E2E. Журналы стенда: `output/v5-lab/phase7-debian12-e2e-r3.log`,
`output/v5-lab/phase7-debian13-e2e-r2.log`, `phase7-wireguard-nat-wsl.log`.
